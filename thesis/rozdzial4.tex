\chapter{Implementacja}

Rozdział niniejszy opisuje implementację systemu badawczego — strukturę kodu, implementację mikroserwisów, konfigurację \textit{Kubernetes}, infrastrukturę monitorującą oraz skrypty automatyzujące. Wszystkie listingi odwołują się do rzeczywistych plików w repozytorium projektu.

\section{Struktura repozytorium}

Kod projektu jest zorganizowany w następującej strukturze katalogów:

\begin{verbatim}
magisterka/
  apps/
    cpu-service/         # CPU-bound microservice
    io-service/          # I/O-bound microservice
    echo-server/         # Auxiliary echo service
    memory-service/      # Memory-bound microservice (extension)
  k8s/
    base/                # Namespace
    cpu-service/         # Deployment + Service + HPA x3
    io-service/          # Deployment + Service + HPA x3
    echo-service/        # Deployment + Service
    memory-service/      # Deployment + Service + HPA
    monitoring/          # Prometheus Adapter config
    ingress.yaml         # Traefik Ingress (legacy, nieużywany na GKE)
  monitoring/

  scripts/
    deploy-k3s.sh        # Skrypt wdrożeniowy (legacy, GKE używa kubectl apply)
    run-tests.sh         # Test orchestration (8 scenarios)

  tests/
    k6/                  # k6 load test scripts
  docs/
    prd.md               # Product Requirements Document
  docker-compose.yaml    # Opcjonalny development (nieużywany w badaniach)
\end{verbatim}

\section{Implementacja mikroserwisów}

Każdy mikroserwis jest zaimplementowany jako niezależna aplikacja \textit{FastAPI} (Python 3.12), konteneryzowana za pomocą \textit{Docker} i uruchamiana przez \textit{Uvicorn} (serwer ASGI).

\subsection{Wspólne cechy implementacyjne}

Wszystkie serwisy dzielą następujące cechy:

\begin{itemize}
  \item \textbf{FastAPI + Uvicorn} — framework \textit{FastAPI} 0.115.6 z serwerem \textit{Uvicorn} 0.34.0. Wybór \textit{FastAPI} podyktowany jest natywną obsługą asynchroniczności (\texttt{async/await}), automatyczną generacją dokumentacji OpenAPI oraz lekkością.
  \item \textbf{Dockerfile} — identyczny wzorzec dla wszystkich serwisów: obraz bazowy \texttt{python:3.12-slim}, instalacja zależności przez \texttt{pip install --no-cache-dir}, aplikacja kopiowana jako pojedynczy plik \texttt{main.py}.
  \item \textbf{Prometheus metrics} — automatyczna instrumentacja przez \texttt{prometheus-fastapi-instrumentator} 7.0.0, która wystawia metryki HTTP (liczniki żądań, histogramy czasu odpowiedzi, liczba żądań w toku) na endpointzie \texttt{/metrics}.
  \item \textbf{Health check} — endpoint \texttt{GET /health} zwracający \texttt{\{"status": "ok", "service": "..."\}}, wykorzystywany przez \textit{liveness} i \textit{readiness probes} w \textit{Kubernetes}.
  \item \textbf{CORS} — middleware \texttt{CORSMiddleware} z zezwoleniem na wszystkie źródła (\texttt{allow\_origins=["*"]}) dla wygody testowania.
\end{itemize}

\subsection{CPU-service}

\texttt{cpu-service} implementuje dwa endpointy obciążające procesor:

\subsubsection{POST /process — przetwarzanie obrazu}

Endpoint akceptuje obraz w formacie \textit{multipart form-data}, wykonuje 5-etapowy potok przetwarzania CPU-intensywnego z użyciem biblioteki \textit{Pillow} 11.1.0:

\begin{enumerate}
  \item Konwersja do skali szarości (\texttt{image.convert("L")}).
  \item Zastosowanie filtru \texttt{BLUR}.
  \item Zastosowanie filtru \texttt{SHARPEN}.
  \item Zastosowanie filtru \texttt{FIND\_EDGES}.
  \item Ekstrakcja kanałów RGB i resize.
\end{enumerate}

Po przetworzeniu, dla każdego kanału obliczana jest entropia Shannona według wzoru:

\begin{equation}
  H = -\sum_{i=0}^{255} p_i \log_2(p_i), \quad \text{gdzie } p_i = \frac{\text{histogram}[i]}{\text{total\_pixels}}
\end{equation}

\subsubsection{GET /fibonacci — ciąg Fibonacciego}

Endpoint oblicza $n$-tą liczbę Fibonacciego rekurencyjnym algorytmem o złożoności $O(2^n)$. Parametr $n$ jest pobierany z \textit{query string} (domyślnie 25). \subsection{IO-service}

\texttt{io-service} implementuje dwa endpointy symulujące operacje I/O:

\subsubsection{GET /query — łańcuch opóźnień asynchronicznych}

Endpoint wykonuje sekwencję wywołań \texttt{asyncio.sleep()} z konfigurowalnymi parametrami:

\begin{itemize}
  \item \texttt{delay} (domyślnie 100\,ms) — bazowe opóźnienie pojedynczego kroku.
  \item \texttt{steps} (domyślnie 3) — liczba kroków w łańcuchu.
  \item \texttt{jitter} (domyślnie 0.2) — losowy rozrzut $\pm20\%$ wokół \texttt{delay}.
\end{itemize}

Całkowity czas odpowiedzi wynosi $\text{steps} \times \text{delay} \times (1 \pm \text{jitter})$, a procesor pozostaje bezczynny podczas oczekiwania (\texttt{asyncio.sleep} zwalnia wątek). Dzięki temu zużycie CPU nie koreluje z liczbą żądań — serwis jest czysto \textit{I/O-bound}.

\subsubsection{GET /upstream — wywołanie zewnętrzne}

Endpoint przekazuje żądanie do \texttt{echo-server} za pomocą \texttt{httpx.AsyncClient} z timeoutem 10 sekund i zwraca odpowiedź z dodatkowym opóźnieniem symulującym przetwarzanie. Parametry: \texttt{delay} (domyślnie 50\,ms), \texttt{jitter} (domyślnie 0.1).

\texttt{io-service} wystawia trzy niestandardowe metryki:

\subsection{Echo-server}

\texttt{echo-server} jest minimalistycznym serwisem pomocniczym z dwoma endpointami: \texttt{GET /health} i \texttt{POST /echo}. Endpoint \texttt{/echo} zwraca kopię otrzymanego żądania (nagłówki, \textit{body}, parametry), umożliwiając weryfikację poprawnego przekazywania danych przez \texttt{io-service} w scenariuszu \texttt{external\_calls}.

Serwis korzysta z biblioteki \texttt{httpx} do opcjonalnych wywołań zwrotnych do \texttt{io-service} i rejestruje niestandardowe liczniki \texttt{echo\_server\_echoes\_total} oraz \texttt{echo\_server\_upstream\_calls\_total}.

\subsection{Memory-service}

\texttt{memory-service} implementuje pamięciową bazę klucz-wartość (\textit{in-memory cache}) z limitem 10000 wpisów (\texttt{MAX\_CACHE\_ENTRIES}). Udostępnia pełne CRUD dla cache: \texttt{GET /cache}, \texttt{GET /cache/\{key\}}, \texttt{POST /cache/\{key\}}, \texttt{DELETE /cache/\{key\}}, \texttt{DELETE /cache}.

Endpoint badawczy \texttt{POST /cache/fill} wypełnia cache danymi testowymi o kontrolowanym rozmiarze — parametry \texttt{sessions} (liczba wpisów, 1--5000) i \texttt{size\_kb} (rozmiar pojedynczego wpisu w KB, 1--5000). Wartości są generowane przez \texttt{random.choices} z alfabetu ASCII, co zapobiega optymalizacji \textit{string-interning} Pythona.

\subsection{Services — LoadBalancer w GKE}

W odróżnieniu od typowego środowiska deweloperskiego (gdzie stosuje się \texttt{ClusterIP} z \texttt{port-forward}), wszystkie serwisy aplikacyjne są typu \texttt{LoadBalancer}. GKE automatycznie tworzy zewnętrzny \textit{GCP LoadBalancer} (Layer 4, TCP) i przydziela mu publiczny adres IP. Ruch z maszyny \texttt{k6-generator} trafia bezpośrednio na ten adres IP, co odzwierciedla warunki produkcyjne.

Plik \texttt{k8s/ingress.yaml} (konfiguracja \textit{Traefik Ingress} z routingiem przez hosty \texttt{*.k3s.local}) pozostaje w repozytorium jako artefakt historyczny, ale \textbf{nie jest używany} w środowisku GKE — komunikacja odbywa się bezpośrednio przez GCP LoadBalancer.

\section{Infrastruktura monitorująca}

\subsection{kube-prometheus-stack — instalacja przez Helm}

Pakiet \textit{kube-prometheus-stack} jest instalowany przez \textit{Helm} — menedżera pakietów dla \textit{Kubernetes}. Instalacja odbywa się trzema poleceniami:

\begin{lstlisting}[language=bash, caption={Instalacja \textit{kube-prometheus-stack} przez Helm}, label={lst:helm-install-code}]
# Dodanie repozytorium Helm
helm repo add prometheus-community \
  https://prometheus-community.github.io/helm-charts
helm repo update

# Instalacja w namespace magisterka
helm install monitoring prometheus-community/kube-prometheus-stack \
  --namespace magisterka --create-namespace \
  --set prometheus.prometheusSpec.serviceMonitorSelectorNilUsesHelmValues=false \
  --set grafana.service.type=LoadBalancer
\end{lstlisting}

Parametr \texttt{grafana.service.type=LoadBalancer} powoduje, że \textit{Grafana} jest eksponowana przez GCP LoadBalancer, co umożliwia dostęp do dashboardów z dowolnej przeglądarki bez konieczności tunelowania.

Pakiet instaluje następujące komponenty:
\begin{itemize}
  \item \textbf{Prometheus} — centralny system zbierania metryk, automatycznie skonfigurowany do wykrywania \textit{ServiceMonitor} i \textit{PodMonitor} w namespace \texttt{magisterka}.
  \item \textbf{Grafana} — platforma wizualizacji z predefiniowanymi dashboardami \textit{Kubernetes}.
  \item \textbf{kube-state-metrics} — generuje metryki o stanie obiektów \textit{Kubernetes} (Deploymenty, HPA, Pody).
  \item \textbf{node-exporter} — zbiera metryki systemowe z węzłów.
  \item \textbf{Prometheus Operator} — zarządza cyklem życia \textit{Prometheusa}.
\end{itemize}

\subsection{Grafana — dashboard i eksport danych}

Dashboard ,,Magisterka — System Overview'' (UID: \texttt{magisterka-overview}) zawiera 16 paneli, odświeżanych co 10 sekund, pokazujących kluczowe metryki w czasie rzeczywistym. \textit{Grafana} jest dostępna publicznie przez GCP LoadBalancer, co umożliwia obserwację eksperymentów na żywo.

Dla każdego scenariusza testowego z \textit{Grafany} eksportowanych jest 5 zestawów danych CSV (poprzez \textit{Grafana render API} lub ręczny eksport):

\end{enumerate}

\section{Skrypty automatyzujące}

\subsection{run-tests.sh — orkiestracja testów}

Skrypt \texttt{scripts/run-tests.sh} ($\sim$780 linii) automatyzuje wykonanie wszystkich 8 scenariuszy badawczych. W środowisku GKE skrypt działa na maszynie \texttt{k6-generator} (\textit{Compute Engine}), która ma skonfigurowany dostęp do klastra GKE przez \texttt{kubectl}:

\begin{enumerate}
  \item \textbf{Sprawdzenie wymagań} — weryfikacja dostępności \texttt{kubectl} i \texttt{k6}.
  \item \textbf{Pętla scenariuszy} — dla każdego z 8 scenariuszy:
    \begin{enumerate}
      \item Przełącza HPA na odpowiednią strategię (funkcja \texttt{switch\_hpa}).
      \item Resetuje \textit{Deployment} do 1 repliki (funkcja \texttt{reset\_deployment}).
      \item Uruchamia test \textit{k6} 5-krotnie (zmienna \texttt{REPETITIONS=5}), z ruchem kierowanym na adresy IP GCP LoadBalancer przez \texttt{options.hosts}.
      \item Zapisuje wyniki do \texttt{results/<scenario>/}.
    \end{enumerate}
  \item \textbf{Cooldown} — po każdym scenariuszu: skaluje oba serwisy do 1 repliki, usuwa wszystkie HPA, czeka 120 sekund na stabilizację.
\end{enumerate}

\section{Podsumowanie implementacji}

Zaimplementowany system badawczy składa się z czterech mikroserwisów (\texttt{cpu-service}, \texttt{io-service}, \texttt{echo-server}, \texttt{memory-service}), infrastruktury monitorującej opartej na \textit{kube-prometheus-stack} (Helm) oraz zestawu skryptów automatyzujących testy. Kluczowe cechy implementacji:

\begin{itemize}
  \item \textbf{Środowisko GCP/GKE} — całość infrastruktury działa na zarządzanym klastrze \textit{Google Kubernetes Engine}, z serwisami eksponowanymi przez GCP LoadBalancer i maszyną \textit{Compute Engine} jako generatorem obciążenia.
  \item \textbf{Monitoring przez kube-prometheus-stack} — instalacja przez \textit{Helm} zapewnia spójny, automatycznie skonfigurowany stos monitorujący bez ręcznych manifestów.
  \item \textbf{Pełna automatyzacja} — skrypt \texttt{run-tests.sh} orkiestruje wszystkie 8 scenariuszy z 5-krotnym powtórzeniem, z automatycznym przełączaniem HPA i cooldownem.
  \item \textbf{Powtarzalność} — każdy scenariusz testowy jest uruchamiany 5-krotnie, z cooldownem między scenariuszami.
  \item \textbf{Odtwarzalność} — wszystkie manifesty są deklaratywne i mogą być odtworzone na dowolnym klastrze GKE.
  \item \textbf{Obserwowalność} — metryki zbierane przez \textit{Prometheusa} i wizualizowane w \textit{Grafanie} (dostępnej publicznie przez LoadBalancer), z eksportem 5 zestawów CSV na scenariusz.
\end{itemize}
